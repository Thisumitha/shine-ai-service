# Team Guide: how to work in shine-ai-service

Read this once before writing code. It explains the folder structure, what goes in each file, and how to add a feature. The design background is in `Shine-AI-Chatbot-Guide.pdf` (what we are building) and `docs/ARCHITECTURE.md` (the layer rules in short).

## 1. Setup

```
git clone https://github.com/Thisumitha/shine-ai-service.git
cd shine-ai-service
git checkout develop
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env          # then fill the values (never commit .env)
uvicorn app.main:app --reload --port 8000
pytest
```

Check it works: open `http://localhost:8000/health`, it returns `{"status":"ok"}`. `__pycache__/` and `.pyc` files are generated by Python and are git-ignored; ignore them.

## 2. The big idea: four layers

A request goes down through the layers and the answer comes back up. Each layer only talks to the one below it.

```
HTTP request
   |
   v
api/routers        (controller)   Receives the request, checks the user, calls ONE service method, returns the response.
   |
   v
services           (business)     The real work: steps of a use case (chat, quiz, indexing...).
   |
   v
domain/ports       (interfaces)   Abstract "what we need" (Embedder, LLMClient...). No real code.
   ^
   |  implements
infrastructure     (adapters)     The real code that talks to Gemini, Chroma, SQLite, the Spring backend, PDFs.
```

Import rules (a pull request that breaks these is rejected):

| File in | May import | Must NOT import |
|---|---|---|
| `api/` | `services`, `domain`, `config` | `infrastructure` directly |
| `services/` | `domain` | `fastapi`, `infrastructure` |
| `domain/` | only the Python standard library | everything else |
| `infrastructure/` | `domain`, third-party libraries | `api`, `services` |
| `container.py` | everything (it wires concrete classes to ports) | n/a |

Why: services never know whether the LLM is Gemini or a fake, so tests run without internet or API keys.

## 3. What to write in each file or folder

### Root of `app/`

| File | Write here | Do not |
|---|---|---|
| `main.py` | `create_app()`: create FastAPI, build the container, `include_router(...)` for every router. Add one line per new router. | business logic |
| `config.py` | One field per setting in `Settings` (type + safe default). Values come from `.env`. Add the same name to `.env.example` (name only, no secret). | read `os.environ` anywhere else |
| `container.py` | `Container` dataclass holding the long-lived objects (settings, services, adapters). `build_container()` creates each adapter once and passes it into the services that need it. | create adapters inside routers or services |

### `api/` (presentation / controller layer)

- `api/routers/<name>.py`: one file per feature area (`health.py`, later `chat.py`, `study.py`, `reports.py`, `internal_index.py`). Contains an `APIRouter`, the endpoint functions, and nothing else. Each endpoint: read input, get the user from the dependency, call one service method, return the result. No `if/else` business rules, no database or HTTP calls.
- `api/schemas/<name>.py` (create when needed): Pydantic request/response models, for example `ChatRequest{course_id, message, session_id}` and `ChatResponse{answer, sources}`. Keep them separate from domain entities.
- `api/deps.py` (step 3): FastAPI dependencies, for example `get_current_user` (reads the bearer token, calls the JWT verifier, returns a `CurrentUser`) and `get_container`.

Router example:

```python
@router.post("/api/v1/ai/chat", response_model=ChatResponse)
def chat(body: ChatRequest, user: CurrentUser = Depends(get_current_user),
         container: Container = Depends(get_container)):
    return container.chat_service.answer(user, body.course_id, body.message)
```

### `services/` (application layer)

One class per use case, file named after it: `chat_service.py`, `ingestion_service.py`, `quiz_service.py`, `flashcard_service.py`, `summary_service.py`, `progress_service.py`, `report_service.py`.
- The constructor receives ports (`Embedder`, `LLMClient`, `Retriever`, `ChatStore`, `CourseAccess`...), never concrete classes.
- Methods express the steps of the use case in plain order (for chat: check access, rewrite question, search, answer, self-check, save).
- Raise our own errors from `domain/errors.py` (for example `AccessDenied`, `NotFound`), not `HTTPException`. The router layer turns them into HTTP codes.

### `domain/` (the core, no frameworks)

- `domain/entities/`: plain dataclasses that describe our data. `user.py` has `CurrentUser(email, role, user_id)`. Add `chunk.py`, `document.py`, `message.py`, `source.py` here.
- `domain/ports/`: abstract classes (`ABC`) that describe what the services need, signatures only. Existing: `course_access.py`, `embedder.py`, `llm_client.py`, `ocr_engine.py`, `retriever.py`, `chat_store.py`. Add a new port here first when a service needs a new ability.
- `domain/errors.py` (create when needed): the shared exception classes.

### `infrastructure/` (adapters: the real code)

Each class implements one port.

| Folder | Write here (files) | Implements |
|---|---|---|
| `auth/` | `jwt_verifier.py`: verify HS256 token with `JWT_SECRET`, email from `sub`, `role`, `userId`; reject expired. `access_guard.py`: combine role + enrolled courses. | used by `api/deps.py` |
| `clients/` | `spring_client.py`: calls the Spring backend with `httpx` (enrollment, teacher courses), 60 s cache. `game_client.py` (later): XP award. | `CourseAccess` |
| `ingestion/` | `pdf_loader.py`, `text_cleaner.py`, `chunker.py`, `ocr_gemini.py`, `ocr_tesseract.py`, `pipeline.py` | `OcrEngine` |
| `retrieval/` | `embedder_gemini.py`, `sparse_index.py` (TF-IDF), `dense_index.py`, `hybrid_retriever.py`, `reranker.py`, `query_rewriter.py`, `math_trace.py` | `Embedder`, `Retriever` |
| `store/` | `vector_store.py` (ChromaDB), `document_registry.py` (SQLite: PDF status) | internal stores |
| `llm/` | `gemini_llm.py` | `LLMClient` |
| `memory/` | `sqlite_chat_store.py` | `ChatStore` |

Rules: never put API keys or URLs in code (read from `Settings`). Convert library errors into plain domain errors.

### Other folders

- `tests/`: mirror `app/` (for example `tests/infrastructure/test_jwt_verifier.py`). Use fake ports, no network. Every new class needs at least one test, including a failure case.
- `evaluation/`: the accuracy test set (`dataset.jsonl`) and `run_eval.py` (later phase).
- `scripts/`: one-off tools such as `backfill.py` (index all existing PDFs).
- `docs/`: this guide and the architecture notes. Update them when structure changes.

## 4. How to add a feature (worked example: a "list my chat sessions" endpoint)

1. **Domain:** add `Session` entity in `domain/entities/session.py`. If storage is new, add a method to `ChatStore` in `domain/ports/chat_store.py`.
2. **Infrastructure:** implement that method in `infrastructure/memory/sqlite_chat_store.py`.
3. **Service:** add `SessionService.list_for(user)` in `services/session_service.py`, using only the `ChatStore` port.
4. **Container:** create the service in `container.py` and add it to `Container`.
5. **API:** add the schema in `api/schemas/` and the endpoint in `api/routers/` (call the service, return the result). Register the router in `main.py`.
6. **Tests:** service test with a fake `ChatStore`; endpoint test with `TestClient`.
7. Run `pytest`, then open a pull request into `develop`.

## 5. Security rules everyone must follow

- The user's identity comes only from the verified token. Never use an email, user id or course list sent by the browser to decide access.
- Every search must carry the course ids approved by the server for that user.
- Secrets (`JWT_SECRET`, `INTERNAL_SECRET`, `GEMINI_API_KEY`) live in `.env` only, never in code, tests or commits.
- Internal routes (`/internal/*`) require the `x-internal-secret` header.
- Users only see short friendly messages; technical details go to the log.

## 6. Git workflow

- `main`: stable. `develop`: integration. Work in `feature/<short-name>` created from `develop`. Never commit directly to `main` or `develop`.
- One task per branch. Commit small and often. Merge into `develop` with a pull request (`--no-ff`) after `pytest` passes.
- Commit messages: plain English, imperative, say what changed and why if not obvious. One topic per commit.
  - Good: `Reject expired tokens in the JWT verifier`, `Add Spring client with 60 second enrollment cache`.
  - Bad: `update`, `fix stuff`, `changes`.
- Do not commit `.env`, `.venv/`, `data/`, or `__pycache__/`.

## 8. Checklist before opening a pull request

- [ ] Imports follow the table in section 2
- [ ] No business logic in routers, no FastAPI in services
- [ ] New settings added to `config.py` and `.env.example`
- [ ] `pytest` passes, new code has tests including a failure case
- [ ] No secrets, no `.env`, no generated files committed
- [ ] Commit messages are clear and one topic each
